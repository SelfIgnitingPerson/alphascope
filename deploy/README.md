# 公网部署

仅把应用放进这台Mac的Docker、继续连接本机MySQL，请使用[本机Docker启动](local-docker.md)。下面的PUBLIC方案包含独立MySQL容器，与本机个人模式分开。

这是与本机开发分开的生产入口。每位账号拥有独立自选、持仓、指标、规则、报告、实验和任务；公开基础行情与目录共享。首次部署使用空数据库，不把现有私人开发库直接放到公网。

1. 将production.env.example复制为本目录.env，设置权限600，填写实际域名、证书邮箱、数据库口令及至少12字符的管理员初始密码；邀请注册默认关闭。
2. 配置域名解析，确认80/443端口可达，运行`docker compose --env-file deploy/.env -f deploy/compose.yml config --quiet`。
3. 运行`docker compose --env-file deploy/.env -f deploy/compose.yml up -d --build`。migrate一次性容器使用管理员连接执行Flyway和预算触发器DDL，成功后backend才启动；管理员凭据不传入backend，不修改MySQL全局权限。只有网关对外开放，数据库与后端不发布主机端口。一次性schema服务先以管理员连接执行Flyway和触发器DDL，完成后才启动使用专用普通账号的backend；管理员凭据不传给backend，不修改MySQL全局权限。
4. 访问HTTPS域名，使用配置的管理员账号登录。首次创建后不会因为环境变量变化重置密码；账号管理入口负责恢复密码并撤销旧会话。
5. 在产品运行页核对来源许可、实际数据日期、队列与存储预算。许可没有依据或过期时保留未就绪状态，不能靠登记按钮获得供应商授权。按实际取得的使用范围配置后，再试运行首次研究。
6. 用两个普通账号验收各自空白自选、互不可见的报告和任务，以及无法访问管理员接口。日历和行情具备实际可用证据后，才开启日常调度。

前后端合为一个生产JAR，使用同源Cookie；不使用Vite开发服务提供公网访问。容器以非root账号运行，根文件系统只读；运行目录和数据库各用独立持久卷。TLS由Caddy终止，后端不根据X-Forwarded-For授权；PUBLIC模式拒绝无会话、越权及缺失CSRF的写入。

## 发布与升级

源码阶段仍只有当前V1。第一次实际发布后冻结该基线，不再编辑已发布的V1或修复校验和；后续结构变化使用正常增量迁移，并用上一正式版本的库进行升级测试。`upgrade-schema-direct`只用于已明确授权的开发库，不能成为生产自动升级入口。

记录本次源码、JAR、镜像摘要与SQL指纹。生产构建禁止部署SNAPSHOT依赖或仅凭可变latest标签识别版本；当前示例版本标签应在发布后绑定并记录镜像digest。正式变更前停止新的任务领取，等待或取消运行任务，检查队列与当前数据库版本，再切换经过验收的镜像。

只能回滚至**相同隔离协议和兼容数据库结构**的镜像，不能回滚到此前没有租户隔离的本地版JAR，否则旧代码可能越过新身份边界。旧二进制回滚不等于数据库回滚；涉及不兼容结构时必须提供受测的前向修复方案。

## 数据保护与监控

当前配置按用户要求关闭自动备份，不创建恢复点，也不挂载Docker socket。公开托管前由部署方明确恢复目标和数据保护方式，不能把MySQL持久卷视为备份。已有隔离恢复工具的操作说明在[运行维护](../docs/runbook/local-development.md)。

业务状态以应有交易日、实际行情日期、任务质量和队列为准，health UP只表示服务技术健康。持续记录任务成功率、阶段耗时、待处理数量及证据字节；首先确认实际连续交易日的运行结果，再承诺服务时效。外部域名、TLS签发、商业许可、持续运行和远程CI均须在实际部署环境验收，本地构建不能替代。
